# Kubernetes CrashLoopBackOff — startup failure and backoff

Runbook ID: RB-K8S-001
Category: kubernetes
Signals: CrashLoopBackOff | Back-off restarting failed container
Summary: A container repeatedly exits after startup, so kubelet backs off restarts; previous logs and termination state identify the underlying application failure.
Sandbox commands: kubectl logs deploy/sentinel-demo --previous | kubectl rollout undo deploy/sentinel-demo

## Scope and safety
Kubernetes sentinel-demo workload. CrashLoopBackOff is a waiting state, not the root cause itself.

These are synthetic training incidents, not records of a real outage. All commands in SentinelOps execute only as sandbox receipts. Confirm impact, affected scope and change ownership before a real operator takes action.

## Symptoms and error evidence
The synthetic release referenced a missing configuration key. Previous container logs showed startup validation failure and repeated exit code 1.

Preserve timestamps and sanitized request/event IDs. Treat one symptom as evidence to investigate, not proof of a single cause.

## Diagnostic procedure
1. Read kubectl logs deploy/sentinel-demo --previous and inspect the last termination reason and exit code.
2. Compare deployment revisions, ConfigMaps, Secret references, readiness/startup probes and container command/args.
3. Inspect events and node conditions. If termination says OOMKilled, use the memory runbook rather than assuming bad configuration.

## Root cause hypothesis
A container repeatedly exits after startup, so kubelet backs off restarts; previous logs and termination state identify the underlying application failure. Correlate this hypothesis with the diagnostic results and the most recent authorized change. If the evidence contradicts it, stop and retrieve additional context rather than executing the proposed plan.

## Remediation and approval
Fixed simulation plan: `kubectl logs deploy/sentinel-demo --previous` followed by `kubectl rollout undo deploy/sentinel-demo`. The second action is mutating and requires human approval. These commands are recorded as simulation receipts, never executed by a shell.

1. Request approval for a controlled rollback of the fixed sentinel-demo deployment in simulation.
2. For a real rollout, verify revision history and compatibility of configuration/database changes before rollback.
3. Avoid repeatedly deleting pods; the controller will recreate the same failing specification.

## Validation and rollback
Success criteria: The desired replica count becomes ready, restart counts stabilize and application probes pass through the observation window.

Rollback: Restore the last verified compatible revision; stop if an irreversible schema migration prevents safe rollback.

Record before/after evidence and the change approver. Recovery must be verified by real monitoring; a successful simulation is not production recovery.

## Synthetic post-mortem and prevention
A configuration reference was not validated in CI. Add manifest validation, staged rollout and startup-path tests.

The incident owner should document the detection gap, contributing change, remediation evidence and follow-up owner. An incomplete RCA should remain a hypothesis until independently validated.
